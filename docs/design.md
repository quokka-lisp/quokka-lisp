## Vision and principles

Quokka is one live Lisp world — VM, language, editor, UI and tools in a single image — small enough for one person to understand completely. It is browser-first via WASM, runs natively inside a desktop app shell, and never on bare metal. It takes its soul from the Lisp machines, its malleability from Smalltalk and its discipline of smallness from Oberon, with a modern look.

**Principles**

1. **One world.** Editor, debugger, UI and your code are objects in the same image. No separate editor process talking over a socket.
2. **Comprehensible.** The whole system should be readable by one person. That comes from keeping it small and its concerns separate — Rust only below the primitive table, each crate one thing — not from a line count: an early proposal to hold the Rust core under 15k lines was dropped on 25 Nov 2026 ([#89](https://github.com/quokka-lisp/quokka-lisp/issues/89)) as an artificial figure that took attention from building the system well.
3. **Text is executable.** Any S-expression on screen can be evaluated where it stands. There is no separate shell.
4. **Output remembers its object.** Everything printed stays linked to the live object it represents, so you can point at it, inspect it and act on it.
5. **Errors are conversations.** An error stops and asks; it never throws away state. You fix the code and resume.
6. **Modern look, old soul.** Proportional type, HiDPI, light and dark themes, tiled viewers. No 1985 bitmap aesthetic.

**Non-goals:** running Genera or Medley software, bare-metal drivers, ANSI Common Lisp compliance, multi-user security.

## Inheritance

Each tradition is strongest where the others are weak, so we take three ideas from each and leave behind its main burden.

*[Diagram: inheritance — three traditions, one synthesis]*

| Tradition | What we take | What we leave behind |
| --- | --- | --- |
| Lisp machines (Genera, Interlisp-D) | Tagged objects in one image; presentations (live output); conditions and restarts | Sheer size |
| Smalltalk (Squeak, Pharo, Glamorous Toolkit) | Direct manipulation; browsers over live code; moldable inspectors | Image-only code |
| Oberon ([Project Oberon](https://people.inf.ethz.ch/wirth/ProjectOberon/index.html), Acme) | Smallness as a goal; text as executable commands; tiled viewers, no overlaps | Static modules |

The combination that none of the three had on its own: Oberon's executable text becomes Lisp S-expressions, and their results come back as live presentations inside the same text.

## Architecture overview

The system has five layers and one hard boundary: Rust below it, Lisp above it.

*[Diagram: architecture — five layers, one boundary]*

| Layer | Language | Contents |
| --- | --- | --- |
| Environment | Lisp (in the image) | Tiled viewers, live text, listener, inspector, browser, debugger |
| Presentation and UI toolkit | Lisp (in the image) | Presentation types, commands, layout, incremental redisplay, input |
| Language and runtime library | Lisp (in the image) | Compiler, conditions and restarts, generic functions, streams, packages |
| *Primitive table* | — | *The only door between Lisp and Rust* |
| VM core | Rust (host program) | Bytecode interpreter, tagged heap, garbage collector, image save and load, processes |
| Host layer | Rust (host program) | Display protocol renderer (DOM and canvas), sound player (Web Audio in the browser), browser storage, network, clock; Tauri shell for native |

Rust supplies only what a Lisp machine's hardware and microcode once did. Everything a user sees or changes — including the compiler and the window system — lives in the image and can be edited while it runs.

## Substrate: the Rust VM

The substrate is a small Rust program that plays the role of Lisp machine hardware: tagged words, a garbage-collected heap, a bytecode interpreter and an image file. Everything above it is Lisp.

**Tagged words.** Every value is one 64-bit word, tagged in its low bits like Ivory's tagged memory. Heap objects are 8-byte aligned, so the low 3 bits are free for the tag. Proposed scheme:

| Low bits | Meaning | Notes |
| --- | --- | --- |
| `xx0` | Fixnum | 63-bit integer, arithmetic without untagging |
| `001` | Cons pointer | The most common heap object gets its own tag |
| `011` | Heap object pointer | Header word gives the type: symbol, vector, string, closure, code, instance, hash table |
| `101` | Immediate | Characters, `nil`, `t`, unbound marker |
| `111` | Reserved | Forwarding pointers during GC |

**Object headers.** A heap object (tag `011`) starts with a header word giving its type and its length in slots: `[ length : 48 ][ type : 8 ][ subtag : 5 ][ 101 ]`. Cons cells have no header — the tag is the type — which is why they get a tag of their own.

That creates a problem the encoding has to solve. The collector scans to-space linearly, so at every position it must know how big the object there is, and a header and a cons cell's car sit in the same place. Giving conses a header too would cost a third more memory on the commonest object in a Lisp. Instead the header is encoded in the immediate space under a subtag that is never handed out, so no value can be mistaken for one: the scan is a single test, and conses stay two words.

The type says whether the object's slots are values. Strings, code and bignums hold raw words, and tracing those would follow numbers as if they were references, so this distinction is load-bearing rather than descriptive.

**Garbage collection.** A simple copying (Cheney) collector: easy to get right and to read. It stays until a measurement says otherwise, and what replaces it is decided (#86, 25 Nov 2026):

- **A generational collector, when a pause is longer than a frame.** Cheney copies everything alive at every collection, so one pause grows with the world. A generational collector keeps new objects in a small *nursery* and collects only that most of the time, since most objects die young. It is built when a collection of a real world is measured at more than **16 ms**, one frame at 60 a second, and not before; #85's trigger already keeps the *total* cost proportional to allocation, so the length of one pause is the only thing left to wait for. Rejected: staying with Cheney for good (the pause has no bound), and incremental copying after Baker (the copy is spread over slices, at the price of a *read* barrier on every `car`, `cdr` and slot, the most expensive kind).
- **The store barrier is in place now, and empty.** A nursery collection must find every reference into the nursery without scanning the old objects, and an old object comes to hold one only by being written to. So each such write has to be noted in a *remembered set*. Every store of a reference into an existing object goes through three methods of `Mutation` — `set_car`, `set_cdr`, `set_slot` — and each calls `Storage::note_store(holder)`, which does nothing yet. Raw slots hold no references and the registers are roots. The call is there before the collector because finding every store again later costs more with each line of Rust written.
- **Weak references: weak pointers and weak-key `eq` tables, without ephemeron semantics**, built in phase 4 with the output records that first need them. A Cheney collector takes both the standard way (GC Handbook §12.2): a weak object is copied without tracing its weak slot and threaded on a list, and after the scan each weak slot is updated if its referent was forwarded and cleared if not. An *ephemeron* is a weak-key entry whose value does not keep its own key alive; that needs a fixpoint in the collector, most programs never notice the difference, and it can be added later without changing an object's layout.
- **A table keyed by address rehashes after a collection, in chunks.** As SBCL's `eq` tables do: a table whose keys the collector moved is stale and is rebuilt at its next use (#64). The rebuild of a large table is to be resumed across slices and not done in one step (rule 9). Rejected: a hash kept in the header (conses have no header, so cons keys would still rehash) and a side table from object to hash (itself keyed by address). A generational collector makes the question smaller, since an old object rarely moves.

Cheney needs no auxiliary stack: `scan` trails `free` through the objects already copied in to-space, so to-space is its own work queue. A loop, not a recursion, so an arbitrarily deep or tangled object graph costs nothing — which matters more than it would elsewhere, since the wasm32 stack is about a megabyte and fixed at link time. Forwarding pointers (tag `111`) go in an object's first word in from-space, which is safe to overwrite because it is about to be abandoned; they are what keeps shared structure shared and stops cycles looping.

*Torture mode.* The classical version collects on every allocation. That is impossible here and need not be: collection cannot happen inside a mutation and allocation only happens inside one, so the bug it hunts — a value lost across an allocation — is unrepresentable (see Rooting). What remains to hunt is the collector's own mistakes: a mis-sized header, an untraced slot, a root nobody forwarded. So the mode collects at every mutation boundary, pads to-space by a varying amount so nothing lands where it was, and then verifies — walking the heap to record object boundaries and checking every reference points at one.

**Rooting.** A copying collector decides what is alive by tracing from its roots — locations outside the heap holding values — and it cannot see Rust local variables. A value held in a Rust local across an allocation is therefore not stale but dead: the collector concluded nobody wanted it and reclaimed it. Because our references are offsets rather than pointers, the result is a wrong answer rather than a crash, which is harder to notice, not easier.

*How it is prevented:* work on the heap happens inside `Heap::mutate`, and collection cannot happen during a mutation. `mutate` takes `F: for<'h> FnOnce(&mut Mutation<'h>) -> R`; the higher-ranked brand means the closure must work for every `'h`, and `R` is fixed outside it, so no value can be carried out. `collect` takes `&mut self`, which a live mutation borrows, so collecting mid-mutation does not compile. Holding a value across a collection is a compile error, not a convention. Thirteen lines of types, no `unsafe`, no runtime check.

The brand must be *invariant* — `PhantomData<fn(&'h ()) -> &'h ()>`, not `PhantomData<&'h ()>`, which is covariant and would silently permit the escape. Heap-reference constructors are crate-private, since the brand stops a value escaping a mutation but not being invented outside one.

*What it costs:* collection can only happen between mutations, so the heap must absorb whatever one allocates. Cheap **only if mutations stay short** — one evaluator step per mutation gives fine-grained collection for free, and a whole evaluation in one gives none at all.

That sentence was in this document from the start and was implemented nowhere, which phase 1 found three times over: a compiler that looked like it hung, a source file that would not load, a REPL line that died — all one mutation filling the heap with its own garbage. Two things now make it true. `Heap::mutate` collects at the boundary when the heap asks, so no caller has to remember; and `eval::eval_root` drives the machine a slice at a time, each slice its own mutation, passing the form and the answer through the root because a value cannot cross a boundary. `eval_now` keeps the single-mutation shape for prelude forms and anything small. And it protects callers from the collector, not the collector from itself; tracing bugs still need the torture mode.

**Image.** The whole heap can be saved to a file and loaded back ("save world"). Pointers are stored relative to the heap base, so an image loads by relocation or straight `mmap`. Booting means loading an image, not running a build.

**Bytecode, not native code.** A compact stack-based bytecode keeps the VM small and portable, including to WASM. Speed comes later from threaded dispatch and inline caches, not a JIT.

*The shape of it*, decided in #25 before any of it was written:

- **Packed bytes, with each opcode's operand widths fixed.** Not one 64-bit word per instruction, which would be clearer to read and about three times larger (`docs/bytecode.md` measures 2.6 bytes an instruction on real code, correcting an earlier guess of two) — wasm32 is a 32-bit address space, a copying collector doubles every figure, and the image is downloaded in the browser. Fixing operand widths *per opcode* is what keeps this cheap: an instruction's size is then a function of its opcode alone, so jump distances are known in one pass and the branch-relaxation fixpoint that variable-width operands force never arises. Ceilings are compiler errors rather than wraparound — a 16-bit jump offset means a function over 64 KB of code is reported, as the JVM reports the same limit per method.
- **The instruction set is written out** in [`bytecode.md`](bytecode.md): forty opcodes, the frame layout, what each special operator compiles to, and every ceiling that is a compiler error rather than a truncation.
- **The encoding is a boundary.** The compiler emits instructions as lists; an assembler encodes them. Only the assembler, the VM's fetch and the disassembler know the byte layout, so changing it later touches three places and not the compiler.
- **A compiled function is a traced object** holding a raw `Code` object, a constants vector, an arity, a `max-stack` and a name. Constants cannot live inside `Code` because its slots are untraced; `max-stack` lets a call reserve its operand space once, as a JVM class file's `max_stack` does.
- **One evaluator at a time.** The tree-walking interpreter is the *bootstrap* evaluator, not a second production one. It runs the compiler, the compiler builds the image, and from then on only the bytecode VM runs: a form typed at a REPL, or passed to `eval`, is compiled and then run, never interpreted. The interpreter stays in the binary to rebuild an image from source with nothing but `cargo`, and is otherwise cold. This is SBCL's arrangement — `sb-ext:*evaluator-mode*` is `:compile` — and it means compiled and interpreted code never share a stack, a scope or a call.

  One rule keeps it true through the bootstrap: while the compiler is itself interpreted, it evaluates `defmacro` into the interpreter, so an expander is never compiled while its caller is not.

  The cost is that **phase 1 has no half-way image**. The VM must handle every special operator before the image runs at all, because a form the compiler cannot compile is a form nothing can run. The alternative — compile the easy forms and push an interpreter frame for the rest — would get a system running sooner at the price of machinery built to be deleted. Chosen deliberately in #25.
- **A contiguous stack.** Compiled frames are regions of one growable heap vector, not individual `Frame` objects on a cons list: a call pushes words and allocates nothing. Possible precisely because the two evaluators never interleave, so there is no boundary for an unwind to cross. The vector is an ordinary traced heap object, so slicing, image save and the collector are unchanged — except that popped slots are cleared, one store, so that stale values above the stack pointer are not kept alive.
- **Variables keep the environment chain**, with the name scan replaced by a `(depth, index)` pair — which is what `ObjectType::Environment` was shaped for. Flat closures (Dybvig, 1987) and stack-allocated locals are the faster design and need escape analysis to know which variables a closure captures. Deferred because it is compiler work rather than VM work and phase 1 is already a long walk before anything runs; the instruction set will have to change when it arrives, which phase 2's rebuild-from-source makes affordable.

**Literals are read-only.** A string read from source, and a symbol's name, are a distinct heap type that `%set-aref` refuses. CLHS 3.7.1 leaves modifying a literal undefined, which is permission to share literals and no help when a program modifies one: before this, `(setf (aref (greeting) 0) #\J)` edited the source of `greeting` silently. Immutability is also what makes sharing *sound* rather than merely licensed, so coalescing identical literals in an image was possible; measured, it was not worth doing (#26). A program that wants to write characters uses `copy-seq` or `make-string`.

**Constant strings are packed; writable strings are wide** (#44). A constant string whose characters are all Latin-1 is a `PackedString`: a character count in its first raw slot, then eight bytes a word, so `char` is still one shift. Any other constant, and every writable string, holds one Unicode scalar per word. Only constants are packed because only a constant's characters are known for good when it is made; a writable packed string would have to grow in place to accept a `λ`, which no heap object can. Lisp cannot tell the layouts apart. UTF-8 was rejected because it makes indexing a scan; UTF-32 at two per word for every string halved the saving. Image after packages: 478,528 bytes; after `symbol-name` stopped copying, 350,944; packed, 253,912.

**Reified frames.** Stack frames are inspectable and resumable objects. The debugger, restarts and fix-and-retry all depend on this, so it is a VM design constraint from day one.

**Slices.** The VM never runs to completion on its own: it executes a bounded number of steps and returns to its caller, so the browser's event loop keeps turning. This is the same constraint as reified frames arrived at from the other side — an evaluator that can stop and resume cannot keep its state on the Rust call stack, so it is an explicit state machine (SICP §5.4's explicit-control evaluator) whose frames are objects in our heap. Saving an image mid-computation, green threads and an interruptible REPL all fall out of this.

*Who ends a slice:* the caller passes a step budget — `run_slice(budget)` — rather than the VM polling the host or watching a wall clock. Timing stays outside the VM, in the host, where it cannot affect what is computed. Slicing is therefore semantically invisible: the same program takes the same path however it is cut up, which makes runs replayable and lets the phase 3 scheduler be seeded rather than raced. The browser recovers a deadline's responsiveness by adjusting the next budget from how long the last slice took. The native host passes `u64::MAX` and ignores the whole question.

*What it costs:* a budget only bounds time if one step is short, so every primitive must be fast or itself chunked. Two invariants keep slicing invisible: collect on allocation rather than on slice boundaries, and never let Lisp observe the remaining budget.

*Waiting for the outside world:* a third way for a slice to end, `Blocked`. The VM never calls its host. A primitive that needs something from outside — the first is `%read-source` — leaves a **request** in the heap (the `Request` register) and the machine stops; the host reads it with `host::pending`, does the work at once or when a browser Promise resolves, answers with `host::complete`, and runs the next slice, which carries on as if the primitive had returned. This is a blocking system call in miniature, or a completion queue holding one request. Rust `async` and callbacks were rejected for the same reason: neither a future nor a closure can be saved in an image, and a request in the heap can — an image saved while waiting reloads still waiting. The computation cannot observe how long it waited, so blocking keeps slicing invisible. Only the bytecode VM can make a request; the interpreter, which has no I/O, refuses. See #35 and chapter 31.

**Processes.** Lightweight green threads scheduled by the VM, like Genera's processes, on one OS thread to start with. A blocked request becomes a *parked* process: the scheduler runs another instead of ending the slice, and each process holds its own request. The questions phase 3 must answer, and which ones the code must not foreclose before then, are in #34.

**Primitives.** A single table of Rust primitives (arithmetic, allocation, I/O, graphics calls) is the only door from Lisp into the host. Its size is part of what a reader must take in, so each entry should have to justify itself.

## Language layer

Decided: a subset of Common Lisp — a Lisp-2 with CL's names and semantics, growing toward ANSI where it pays — rather than a new dialect. Code written for it should also run in SBCL, which gives us a reference implementation to test against.

**Core features**

- **Conditions and restarts** in the CL style. Signalling does not unwind; handlers and the debugger choose a restart. This is what makes "errors are conversations" work.
- **Dynamic variables** for context (current viewer, current output stream, current package).
- **Generic functions with multiple dispatch**, a small CLOS-like object system. Presentations, commands and inspector views all dispatch on object type, so this is load-bearing, not optional.
- **Packages** for namespaces, kept simple.
- **`defmacro`-style macros**, unhygienic with gensyms. Easier to implement and to read than syntax-case.
- **First-class code objects** that know their source, their definition location and their callers (Masterscope-style cross-reference). Planned for the **start of phase 3** (#55), because its gate — fix a function from inside an error — needs the function's source, and so does the inspector. Until then a compiled function keeps only bytecode: a definition typed into the world loses its text, and code compiled before a macro changed keeps the old expansion. With source kept per definition, the world can **recompile what it holds** (all of it, or only what a changed macro reaches, via the cross-reference) instead of reloading files — Smalltalk's `compileAll`, Genera's *Compile Changed Definitions*.

**Bootstrap path**

1. **Interpreter (phase 0):** a small tree-walking interpreter in Rust, grown just far enough to run the compiler's source: macros, closures, a minimal condition system. *(This list once said "special variables" too; the interpreter never had them, and does not need them — they are tier 1, compiled only, #40.)*
2. **First build:** the interpreter runs the CL compiler, which compiles itself and the core library to bytecode and saves the first image. Slow, but it happens once. *Built: `boot::build_image` (#33) — two passes, compile everything with the interpreted compiler and then run the results on the VM, followed by a heap scan proving nothing interpreted survived.*
3. **Fixpoint:** the compiled compiler, now running in the image, rebuilds itself. When its output matches the first build byte for byte, the system is self-hosting.
4. **Afterwards:** the image rebuilds itself, in the browser too. The interpreter stays as a debugging fallback and a way to rebuild from source with nothing but `cargo`.

The compiler is written once, in CL. The build needs only `cargo`, and SBCL is a test oracle rather than a build dependency: code that runs in both must give the same results.

**Source of truth.** Smalltalk's weak spot is that code lives only in the image, which fights version control. Every definition has a canonical text form, saved per module to files on a file host (see Files and storage). On native builds these are plain files that Git can diff and merge. The image is a fast, live cache of those files, and editing a definition in the image writes the file back.

### The CL subset boundary

The subset grows in three tiers, each the minimum needed to unlock a phase. ANSI conformance is measured as we go rather than promised up front.

*[Diagram: CL subset — three tiers and what is deferred]*

| Tier | Unlocks | Contents |
| --- | --- | --- |
| Tier 0 | Runs the compiler · phase 0 | 22 of 25 special operators; `defmacro` with full lambda lists; fixnums, conses, symbols; strings, vectors, hash tables; `defstruct`, `error`, `handler-case` |
| Tier 1 | Self-hosting core · phase 2 | All 25 special operators; `setf` expanders, packages; reader, printer (with `*print-circle*`, #64), `eval`, `load`; sequences, basic `format`; double floats, bignums, ratios (decided by #59); arrays of any rank, fill pointers, adjustable and displaced arrays, bit vectors (pulled from tier 2 by #67) |
| Tier 2 | Runs the environment · phases 3–5 | CLOS generic functions; live class redefinition; conditions, restarts, debugger; `loop`, full `format`, streams; pathnames over file hosts |
| Deferred | Until someone needs it | Ratios, complex numbers, the full MOP, pretty-print dispatch, `compile-file` and fasls |

Tier 0 is the first target: it is everything the phase 0 interpreter must support, which is why the compiler's own source is written to stay inside it.

- **The tier 0 rule.** The compiler and core library use only tier 0: no `loop`, no CLOS, only basic `format`. CI also runs the compiler under SBCL as the oracle.
- **Left out of tier 0:** `progv`, `load-time-value` and `symbol-macrolet`. The interpreter can add them later at little cost.
- **Live redefinition is not optional.** Updating existing instances when a class changes (CL's `update-instance-for-redefined-class`) is in tier 2, because a live environment depends on it.
- **Floats by phase 4.** Graphics needs double floats, so they arrive in tier 1 even though the compiler barely uses them.
- **Measuring conformance.** The ANSI test suite (ansi-test) runs per tier; each tier is defined by which test groups must pass.
- **Quokka extensions** (processes, presentations, file hosts, weak references) live in their own packages, never in `COMMON-LISP`.

## Environment and UI

The screen is a set of tiled viewers holding live text: any form can be run where it stands, and every result stays a live object you can point at and act on.

*[Diagram: screen mock-up — listener, editor and inspector in tiled viewers]*

One interaction loop runs through everything: evaluate a form, get presentations back, pick a command that fits the object's type, and land in another viewer with the object itself.

- **Tiled viewers.** Oberon-style tracks: a wide main track and a narrow tool track. Viewers split and resize but never overlap. Rooms-style workspaces come later, as named sets of viewers per task. This is a want, not a default — overlapping windows are what a system grows if nobody decides otherwise, and Oberon's own reason for rejecting them (too much complication for too small an advantage, 1987) is rule 7 in other words. What is still open is the *model*: fixed tracks or a tree of splits, keyboard-driven or mouse-driven, and whether the display protocol can express layout at all — because if it cannot, the window manager ends up in the renderer where Lisp cannot change it. See [#21](https://github.com/quokka-lisp/quokka-lisp/issues/21).
- **Live text.** Every viewer is a rich-text document mixing prose, code and embedded results. Evaluating a form inserts its result below it as a presentation, so notes, scratch code and the command line are the same thing.
- **Presentations.** Each printed object keeps a reference to the object and its presentation type. When a command needs an argument, clicking any matching presentation on screen supplies it, as Genera's `accept` did. Drawings are presentations too: a shape on a canvas knows the object it draws.
- **Point at anything.** Right-clicking any output gives the commands that fit what it is, and always *Inspect* and *Show the code that drew this*. For the second, every output record remembers the function that produced it, which is a requirement on the display protocol of phase 4.
- **Moldable inspectors.** Objects add views by defining methods on one generic function. A heap object might show its tag and raw words, a file its text, a function its callers, a number in a running program a slider.
- **Debugger as a viewer.** An unhandled condition opens a viewer with frames as presentations and restarts as commands. You edit the failing function in place, then retry the frame. For a name that is not defined, a handler written in Lisp offers the nearest defined names as restarts ("Use `ADD-RECORD` instead"), which SBCL does not.
- **Running programs are processes.** A game loop or an animation runs in its own process beside the listener, so the listener still answers. Clicking a drawing in a running program suspends that process and inspects the object, and continuing resumes it, which is the debugger stopping a process for a reason other than an error.
- **Editor.** Text with structural (paredit-style) commands, editing one definition at a time; a whole package can be opened as text when many definitions change at once (see *The world is a database of definitions*).

### Who it is for

We designed the environment around three kinds of user, and the first of them is the one it has to please first.

1. A **beginner** writes snippets and small programs while following a Lisp book or tutorial, such as *Practical Common Lisp* or *Land of Lisp*. This is also how we expect to use Quokka first ourselves.
2. A **medium user** browses the system to see how it is made, as people do in Smalltalk, and changes small things by following tutorials on the Quokka website: how the tiles look, a colour scheme, the listener's prompt. The same user writes whole applications with a user interface, graphics, sound and MIDI, such as a Rolodex, a small graphics editor, a MIDI player or a platform game.
3. An **advanced user** extends Quokka itself, down to the compiler and the library.

From these we took six use cases. The first four were drawn as mock-ups; the last two are still to be drawn.

1. Follow a book chapter: type the examples, see the results, make a mistake, fix it and go on.
2. Find where something lives: go from something on the screen (the prompt) to the code that drew it, change that code, and see the change at once.
3. Build a small application with a user interface (the Rolodex).
4. Run a program with graphics and sound and change it while it runs (the platform game).
5. Save your work and come back to it the next day.
6. Change the system itself: the compiler or the library, then rebuild and test.

Following a book also sets priorities for the library. Both books lean on `loop`, `format` and files from their first chapters, so a beginner meets missing `loop` long before missing graphics.

### The listener

The listener looks like the transcripts in the books, a prompt such as `CL-USER>` followed by forms and their results, but the transcript is live text like every other viewer. You can scroll up, edit any earlier form and run it again.

An edited form does not run in place. It runs as a new entry at the bottom of the transcript, the old result is struck through, and a note points back to where the form came from. We chose this over running in place, as a notebook such as Jupyter does, because in Lisp the order matters: `*db*` holds whatever every earlier `add-record` left in it, and a notebook run in place can show a page whose state nobody could reproduce by reading it from the top. Appending keeps the transcript a true record of what ran, in the order it ran.

Beside the listener, a small viewer lists the definitions made in this session. From it a scratch session can become something kept: the definitions you tick are committed into a package. This is a beginner's version of what Interlisp-D's *file package* did, which watched what you defined and offered to keep it.

### The world is a database of definitions

A world is not a heap of compiled code with source files somewhere else. It is a live database whose rows are definitions, and files are a view of it, as a dump is a view of a SQL database. We took this from Smalltalk, where methods are objects in the image, and chose it over a file-based environment because the browser, the inspector and the history all want to ask questions of definitions, and a definition that lives in a file has to be found again by parsing.

Each definition is an object holding its name, its kind (function, class, variable, macro, viewer, …), its package, its source text, the compiled object it made, and its versions. Today the compiler throws the source away (`function-lambda-expression` always answers "unknown"), so keeping it is new work, and so is a **who-calls index** that the compiler updates each time it installs a definition, as SBCL's `sb-introspect:who-calls` and Genera's own tables do. Without that index the inspector cannot answer "used by" quickly.

The browser follows the database. Its columns go from systems to packages to definitions, grouped by kind, to the live objects a definition holds (the cards in `*cards*`). Selecting anything opens it in the inspector, which shows its description, what it uses, what uses it, its connections, and its versions, and every name there can be clicked to go on.

Editing a definition and pressing Cmd-Enter **installs it at once**: the world runs the new version from the next call, and the definition is marked as changed since the last commit. A **commit** gives a name and a version number to the state you have installed. We chose this order, Smalltalk's, over Git's (drafts until commit, and the world runs only committed code), because otherwise every experiment would need a commit, or a temporary install that is the Smalltalk model under another name.

Going back comes in two kinds, kept apart on purpose:

1. **Rolling back to a commit** restores definitions and nothing else. Your data (`*db*`, the Rolodex's cards) stays as it is.
2. **Restoring a save point** brings back the whole world as it was, data included. Save points are the image snapshots of *Files and storage*.

One button that did both would undo work you did not mean to undo, which is why the history viewer lists commits and save points separately and draws them differently. Commits grouped by task are Smalltalk's *change sets*; a log of every installed change, which Smalltalk keeps in its *changes file* for recovery after a crash, is the open question of [#24](https://github.com/quokka-lisp/quokka-lisp/issues/24).

Files remain, in three roles. They are how many definitions are changed in one go, how code reaches Git, and how a world is built cold. Once a world is running, the world is the truth: a package is written out as a file ("file out") and read back in ("file in"). Pharo has the same arrangement, with code kept in the image and written to one file per class (its Tonel format, managed by its Iceberg tool) only so that Git has text to version. Quokka's own `lisp/library/` would become such an export, and the warm rebuild that reads it would become filing in a system.

### Systems and packages

You start an application by creating a **system** and an empty package in it, and you fill the package with definitions one at a time, each in its own small editor. The package's own definition, what it uses and what it exports, is the first thing you edit. A stray parenthesis in one definition cannot break its neighbours, because they are not in the same text.

Common Lisp has no sub-packages: package names are flat strings, and `rolodex.import` is a different package from `rolodex` that only looks related. Dotted names are a convention, and package-local nicknames only shorten names. The grouping that CL practice uses is the system, from ASDF's `defsystem`, a named set of components that load and travel together. A Quokka system is an object in the world that **lists its packages explicitly**. The browser suggests dotted names and puts a new `rolodex.something` package into the `rolodex` system by default, but membership is stored, never inferred from a prefix. Systems are a Quokka extension and live in a Quokka package (rule 6).

A package can be opened as text, a view the world generates with a bar marking each definition and its version. Editing several definitions there and installing gives each changed definition its own new version. Exporting a system writes exactly this text, one file per package plus a `system.lisp` naming the packages and, for an application, its main view.

Two consequences follow. A package must remember the **order** of its definitions, because a `defmacro` has to come before its first use and a `defclass` before the methods on it; we proposed creation order, which the text view can change. And **data is not exported**: `*cards*` is written as its `defvar`, not with the cards in it. Data travels with the world or a save point; exporting it as well is an open question, for which CL's hook is `make-load-form`.

### Exporting an application

A system that names a **main view** can be exported as a web page: the page, the VM as WebAssembly, and a stripped world holding the application. Whoever receives it runs it on their own computer, in their browser's sandbox. We considered an app mode, where a link opens your world with the application filling the screen, and rejected it because a world opened from a link runs someone else's code with far less deliberation than downloading and opening an export.

An export comes in two kinds:

1. **Locked**: the editor, the inspector and the browser are stripped out. The world is smaller and simpler. It is not secret: whoever has the file can take the image apart, and the export dialog says so.
2. **Open**: the environment comes along, so the person who receives it can change the application. Their changes form their own change set, which they can export and send back.

Stripping a world is *tree shaking*, which LispWorks calls *delivery*: keep only what is reachable from a root, here the main view, as a garbage collector keeps only what is reachable from its roots. Its known weakness is late binding. A call through `(funcall (intern name))`, `eval` or `find-class` on a computed name reaches code that no reference points at, the shaker removes it, and the application fails only when that path runs; LispWorks offers delivery levels for this reason. The who-calls index makes Quokka's shaker better informed but cannot make it perfect, so how much a locked export keeps (the compiler? `eval`?) is still open. `boot::build_image` already builds a world and then scans its heap to prove what is in it, and a shaken world is the same kind of operation.

### Open questions

- Draw the last two use cases: saving and coming back (5), and changing the system itself (6).
- Whether the Quokka source tree in Git stays a set of files that a world files in, or becomes an export the world writes, and what that does to the cold build and the fixpoint tests, which read `lisp/` today. This reopens the decided *Source of truth* (see *Decisions and open questions*, where a reconciliation is proposed: a commit writes changed packages back to their files).
- How much a locked export keeps, and whether data can be exported with a system.
- The window model of [#21](https://github.com/quokka-lisp/quokka-lisp/issues/21). Every mock-up so far fitted fixed tracks, a track holding a column of viewers, and none needed a general tree of splits; that is evidence for tracks, not yet a decision.

## Display: hybrid renderer

Lisp code describes what to show in Lisp terms, and a small renderer in the page decides how: the DOM for text, canvas or SVG for drawing. HTML never appears in Lisp code.

*[Diagram: display pipeline — Lisp UI code → output records → display protocol → renderer (DOM | canvas/SVG)]*

The display protocol is the boundary between the VM and the screen, so the VM can run as WASM, natively in a Tauri shell, or later on a server, without the Lisp side changing.

**A Lisp-shaped API.** The UI vocabulary follows CLIM: presentation types, commands, formatting macros and drawing functions. A sketch of how it should read (proposed names):

```lisp
(define-presentation-type file-object ())

(define-command (open-in-editor :applies-to file-object)
    ((file 'file-object))
  (edit-file file))

(defun show-directory (dir)
  (formatting-table ()
    (dolist (file (directory dir))
      (formatting-row ()
        (formatting-cell () (present file 'file-object))
        (formatting-cell () (format t "~D bytes" (file-size file)))))))

(defun show-sketch ()
  (with-drawing (:width 240 :height 120)
    (draw-circle* 60 60 40 :ink +accent+)
    (draw-text* "heap" 120 64 :text-style '(:sans :bold :large))))
```

- **Output records.** Every piece of output becomes a record in a tree that Lisp owns. Redisplay compares records, not DOM nodes, as CLIM's incremental redisplay does.
- **Styles, not CSS.** Text styles (family, face, size) and named inks are Lisp objects. A theme maps them to light and dark colours; the renderer turns them into CSS internally.
- **Layout in Lisp terms.** Tracks, viewers, tables and indentation. No box model, margins or tags are exposed to Lisp.
- **Graphics where needed.** A drawing record renders to canvas or SVG; everything else renders to the DOM, so the browser handles text, selection, input methods and accessibility.

## Sound

> **Status: proposed 27 Nov 2026, not decided.** Added while brainstorming the user interface. Nothing here is built, and the open questions at the end are real ones.

Quokka can make sound: a beep when something needs attention, a sound as an object you can inspect and play, and music written and changed while it plays. Sound follows the display's rule: Lisp says *what* to play, in Lisp terms, and a small player in the host decides *how*.

**Why the VM cannot make the samples as they play.** Sound hardware wants a steady stream of numbers, 48,000 of them a second per channel, and it wants each block on time: a block that is late is a click you hear. The VM cannot promise that. It runs in slices whose length the host decides, it has no clock (the slicing section says why, and why that is worth keeping), and a garbage collection can pause it at any moment. So the part with a deadline lives in the host, as the part that draws pixels does. This is the split SuperCollider 3 made in 2002 between its language and its synthesis server, `scsynth`, and that Overtone (Clojure) and Extempore (a Scheme) build on: the language describes and schedules; the server keeps time and makes samples.

**Two ways to make a sound**, both proposed:

1. **Described.** Lisp builds a sound out of a few kinds of parts — oscillators, noise, envelopes, filters, gain, mixing — and asks the host to play it, now or at a time on the *host's* audio clock. In the browser the host builds a Web Audio graph from the description; natively, the same parts in Rust. Notes and phrases are lists of such events, so a melody is data a program can make, print and change.
2. **Computed.** Lisp fills a vector of samples ahead of time, at its own pace, and hands it to the host to play. Nothing here has a deadline, so any sound a program can compute is possible, at the cost of computing it before it is heard.

A sketch of how it might read (proposed names):

```lisp
(beep)                                         ; the system's attention sound

(defparameter *pluck*
  (make-sound (envelope (sine 440) :attack 0.005 :release 0.4)))

(play *pluck*)                                 ; now
(play *pluck* :at (+ (audio-time) 0.5))        ; half a second from now, on the host's clock

(play (sample-sound (make-array 48000 :element-type 'double-float
                                       :initial-contents (my-waveform))
                    :rate 48000))
```

- **Time belongs to the host.** `audio-time` is a host request that answers with the audio clock, and `:at` schedules against it, so a slow slice delays *when Lisp asks* but not *when the sound plays*, as long as it asks far enough ahead. The VM itself still never reads a clock. Animation follows the same rule: the time of the next frame comes from the host (in the browser, `requestAnimationFrame`) as the answer to a host request.
- **A sound is an object.** It prints as a presentation — a waveform you can click to play — and the inspector shows its parts. Errors and the debugger can `beep`, as Lisp machines did.
- **Rust only for the player.** The parts list is small and fixed; anything built from them (instruments, sequencers, music theory, a tracker viewer) is Lisp, by rule 1.
- **The native host needs an audio library** (in Rust, `cpal` is the usual choice, under the permissive Apache-2.0 licence). The browser has Web Audio. A host with no audio answers every sound request with nothing, so programs still run.

**Open questions**

- *Which parts?* Too few and interesting sounds need the computed path; too many and the player becomes a synthesiser to maintain in Rust. Web Audio's own node set is a natural first list.
- *Sound input* (a microphone, for sampling or analysis) — wanted at all? It is a permission the browser asks the user for, like a file.
- *MIDI* — Web MIDI exists in Chromium browsers only.
- *When?* The renderer comes first (phase 4). Sound depends on host requests (#35) and presentations (phase 5), and could land with or after phase 5 without being any phase's gate.

## Files and storage

All file access goes through CL pathnames, whose host component selects a file host behind one protocol. Genera and Interlisp worked the same way for local and network files.

*[Diagram: file hosts — one protocol, four backends]*

Code never knows which backend it is talking to, so the same environment works natively, in the browser and against a remote service.

- **One protocol.** A file host implements a small set of generic functions: open a stream, list a directory, probe, rename, delete, write date. A new backend is just a new class.
- **Image host** (`image:/…`). Files stored as objects in the heap, like Interlisp's `{CORE}` device. Always available, and they travel with the image.
- **Browser host** (`browser:/…`). The browser's Origin Private File System (OPFS). Files persist across page reloads without saving the image.
- **Local host** (`local:/…`). The real filesystem, on native builds only. This is where Git working trees live.
- **Remote hosts (later)** (`cloud:/…`). Files on a server over HTTPS. A documented protocol lets people self-host; a subscription file service can be offered on top. Offline edits need a sync and conflict model, and the Krill Notes Swarm protocol work may carry over.
- **Versions.** CL pathnames have a version component. Hosts that can keep versions (image, remote) expose file history, as Genera's file system did.
- **Image backup.** In the browser, the whole image can be downloaded as a file and uploaded again to restore or move it. Periodic snapshots go to browser storage automatically. What is **not** decided is whether anything records the work *between* two snapshots — a change log, in the prevalence sense, which is also what a user-built in-image database would need. See [#24](https://github.com/quokka-lisp/quokka-lisp/issues/24). The one part that cannot wait, because it constrains the image format phase 1 is fixing, is a monotonic sequence number in the image header saying which point in history a snapshot is.
- **A world reads what its host was given, not what its user can.** A world reaches the outside only through its host, and the native host grants a directory: the current one, or `--root DIR`, plus anything named with `--allow-read PATH`. A name is judged by where it leads once every `..` and every symbolic link has been followed, so neither is a way out. Images are meant to be shared and opening one runs its code; without this a downloaded world could read `~/.ssh`, and keeping credentials out of the image would protect nothing. This is the capability model of WASI's preopened directories. It is not multi-user security, which stays a non-goal: it bounds what an image can touch, not who may run one. In the browser the sandbox is the root. The `local:/` file host will stand on the same grant. Decided 25 Nov 2026 ([#87](https://github.com/quokka-lisp/quokka-lisp/issues/87)).
- **Credentials stay out of the image.** Tokens for remote hosts live in the browser's or OS's credential store, so a downloaded or shared image never carries them. Opening someone else's image means running their code.

## Testing before there is a UI

Every phase is testable from the terminal and in CI long before Quokka has a renderer or file hosts, because the test harness lives in the Rust host, which has the operating system's files and console.

*[Diagram: differential testing — one test file runs on Quokka native, Quokka in WASM and SBCL; results are compared]*

The backbone is differential testing: the same Lisp test file runs on Quokka interpreted and Quokka compiled, natively and in WASM, and on SBCL, and all of them must print the same result.

- **No file system? The host has one.** Before file hosts exist, one host primitive loads source files: `std::fs` natively, WASI in WASM tests, files bundled into the page in the browser. File hosts arrive later on top of it.
- **A terminal REPL from phase 0.** stdin and stdout are enough to drive everything up to phase 3.
- **A browser dev console from phase 0.** A plain page with a text area wired to the WASM VM, long before the real renderer. It proves the browser build works every day.
- **WASM in CI from day one.** The same tests run under wasmtime and in a headless browser, so the browser target never drifts.

| Phase | How it is tested |
| --- | --- |
| 0 · Spike | Rust unit and property tests; GC torture mode (collect on every allocation); differential tests against SBCL |
| 1 · Bytecode and image | Image round-trips (save, reload, compare heaps); interpreted and compiled results must match |
| 2 · Self-hosting | The byte-for-byte fixpoint; ANSI test suite groups for tier 1 |
| 3 · Conditions and processes | Scripted handlers invoke restarts programmatically; seeded, deterministic scheduler tests |

## Decisions and open questions

**Decided**

- [x] **Dialect:** a Common Lisp subset, tested against SBCL as the reference.
- [x] **Bootstrap host:** bootstrap by interpretation — the Rust interpreter runs the CL compiler to build the first image.
- [x] **Subset boundary:** three tiers matched to phases (see The CL subset boundary).
- [x] **Source of truth:** *(under review since 27 Nov 2026: the environment design in* The world is a database of definitions *makes the running world the truth and files a view of it; see the open question below.)* Files on any file host are the truth; the image is a live cache of them. It follows that **images are not committed**: they are build artefacts (`.gitignore` has `*.qi`), rebuilt in seconds by the cold build or the warm rebuild, and a committed one would be an undiffable second truth that every format bump invalidates. The system's own source changes in files and reaches an image by `quokka rebuild`; when the editor lives in the image, editing a definition writes its file back. A browser will load a published image — a CI artefact or release download — not one from the repository.
- [x] **Rooting:** lifetime branding, not a shadow stack. Holding a value across a collection is a compile error. Chosen over an explicit root stack because the Rust surface is small and permanently bounded by rule 1, so the cost of the stricter scheme is bounded too. See Substrate: the Rust VM.
- [x] **Yielding:** the caller passes a step budget (`run_slice(budget)`); no clock and no yield callback in the VM. Chosen over a host-set wall-clock deadline for determinism and replayability. See Substrate: the Rust VM.
- [x] **Browser target:** WASM is first-class from phase 0. The VM runs client-side in the browser, yields to the browser's event loop, and keeps images in browser storage.
- [x] **Rendering stack:** browser-first hybrid renderer (DOM for text, canvas or SVG for drawing) behind a display protocol; native builds in a Tauri shell.
- [x] **Instruction encoding:** packed bytes with per-opcode operand widths, not a fixed 64-bit instruction word. Chosen for size under wasm32's 32-bit address space, and affordable because fixed widths avoid branch relaxation. See Substrate and #25.
- [x] **One evaluator at a time:** the interpreter bootstraps and is then cold; everything a running image evaluates is compiled first. Chosen over a mixed image, which would have bought an earlier running system with a boundary that every unwinding path had to understand. See #25.
- [x] **Host interface:** requests in the heap, answered between slices — not a synchronous trait, not Rust `async`, not callbacks. Chosen before anything was built on the synchronous shape, and because it is the only one of the four an image can save. The interpreter has no I/O. See #35.
- [x] **`tagbody` and `go`:** a `TAG` record that survives a `go` and resumes through a jump table, plus `JMP-TAG`, a one-step jump for a local `go` whose tagbody's record is innermost. Chosen over building `tagbody` from `catch`/`throw` (no VM change, about ten steps a `go`, and the opcodes left unused) and over local jumps with explicit unwinding computed by the compiler (which would need the compiler to track stack depth, where `JMP-TAG` lets the record do it). The bytecode specification's original plan did not survive implementation, and says so. See #37.
- [x] **The image build is Rust, for now:** `boot::build_image` runs during the one moment the system is half built and neither evaluator is fully in charge, and phase 2's self-rebuilding image replaces it. Writing it in Lisp would still need a Rust driver to call it. See #33.
- [x] **Phase 2's scope is all of tier 1**, not only the gate (planning #39). The phase ends when tier 1 is complete and measured against its ansi-test groups *and* the fixpoint holds. The fixpoint is established early (after packages, the Lisp reader and `eval`/`load`) and then kept as a standing test.
- [x] **Tier 1 is a library, compiled only.** The prelude and the compiler stay tier 0, because the interpreter must run them (rule 5). Tier 1 is a third body of Lisp, loaded into the compiled world by the image's own compiler; the interpreter never learns it. Tier-1 differential files run compiled and against SBCL. See #39.
- [x] **Special variables use shallow binding** (#39, #40): the value lives in the symbol, and binding pushes an unwind record holding the old value, restored by `UNMARK` or by the unwinder passing through. Chosen over deep binding for one-load reads and for reusing the record machinery; the cost is that phase 3's thread switch must swap bindings, as Genera's did. Settles item 3 of #34. Implemented in #40: `DBIND` pushes the record; an uncaught error or an abandoned computation also restores every binding left on the stack, since otherwise a binding would outlive the computation that made it.
- [x] **Compiled frames:** a contiguous stack in the heap, which the previous point makes free of boundary problems. See #25.
- [x] **Variables:** the environment chain with `(depth, index)`, not flat closures. Deferred rather than rejected — it is compiler work, and the instruction set will change when it lands. See #25.
- [x] **Literals are immutable:** source strings and symbol names are a separate heap type and refuse mutation, rather than relying on CLHS 3.7.1's "undefined". Chosen because undefined behaviour permits sharing without making it debuggable. See #26.
- [x] **Equal strings do not share storage** (#26, closed 25 Nov 2026). No run-time intern table: it would need weak references and would hash strings of any length in a primitive (rule 9), and SBCL has none. Packing (#44) was the larger win and is done. Coalescing identical *literals* in the image builder, sound since literals are immutable, was the remaining option, and measuring decided it: the system's own sources hold 1,586 string literals with 544 bytes of duplication, against an image of 1.2 MB. Not worth the machinery; reopened if a measured image says otherwise.
- [x] **Strings: Latin-1 constants packed eight to a word** (#44), writable strings one scalar per word. Chosen over two UTF-32 scalars per word for every string (half the saving, one layout) and SBCL's split for writable strings too (a write of a wide character into a narrow string must fail or need an indirection). `symbol-name` returns the symbol's own constant name rather than a copy. Image 478 KB → 254 KB; format version 3.
- [x] **The reader in Lisp reads from string input streams and is readtable-driven** (#45). Streams: a Lisp structure with `read-char`, `peek-char`, `unread-char`, `make-string-input-stream`, `with-input-from-string` — #42's option 1, input half now, output half with the printer (G); chosen over a string-and-index reader whose signature would change when streams arrive. Readtable: the standard macro characters are Lisp functions in `*readtable*`, `#` dispatches, `set-macro-character` works; chosen over a fixed `cond` that would be rewritten when readtables came. Backquote expands exactly as `reader.rs` does, checked by reading the whole system with both readers, because the fixpoint (F) compares compiled bytes. Ratios are refused, not read as symbols (floats are read since #17). Character case and letters are primitives, because Unicode's tables come free with Rust and would be kilobytes in Lisp.
- [x] **The printer in Lisp; console output by host request** (#46). `prin1` and friends are Lisp, with package prefixes by CLHS 22.1.3.3.1 and bars by SBCL's measured rules. Output streams complete #42's option 1: string output streams, and `*standard-output*` as a console stream whose every write is a `%write-console` host request (#35), chosen over a buffer the host drains after each form (output late, every host must remember) and no console yet. Integer division arrived with it (`%quotient`, `rem`; `truncate`, `floor`, `mod` in Lisp). **The differential harness prints with the Lisp printer from step D, not before**: with test files read by the Rust reader, 66 forms printed `QUOKKA::A` for a test's `a`, correctly, because the Rust reader's flat table hands tests the build's own symbols. Making `CL-USER` use `QUOKKA` would have passed at once and reversed #41's "QUOKKA is internal" for good; waiting for the Lisp reader to read the tests changes nothing in the design. Until D the printer is checked by its own SBCL file and by printing the whole system with both printers.
- [x] **`eval` compiles; the read-eval-print loop is Lisp; image hosts read with the Lisp reader** (#47). `eval` is `(funcall (compile-form form))` — #25's one evaluator — and the VM calls a bare compiled `Function` as a closure over nothing. `load` takes a host file name or a stream and rebinds `*package*` and `*readtable*`. The loop is `%host-step` in `eval.lisp` (read one form, `eval`, `prin1`, catch errors), chosen over a Rust loop calling Lisp three times a form; hosts call it through `vm::eval_source`. All image hosts switched at once, chosen over switching only `eval`/`load`: the REPL with an image and the compiled differential leg, which now prints with the Lisp printer as #46 planned. `compile-form` is made re-entrant by saving and restoring its five globals under `unwind-protect`, as `%assemble-lambda` already did, because a macro expander that calls `eval` compiles inside a compilation; before that it silently produced the inner form's code. Concurrent compilation by two processes is a separate question, recorded in #34.
- [x] **The image rebuilds itself, warm, in Lisp** (#48). `%rebuild-world` (`rebuild.lisp`) reads the source in `QUOKKA` with the Lisp reader, compiles every prelude and compiler form with the current compiler, installs them all, then loads the library form by form — the cold build's two passes, chosen over a list of `load`s that would compile late compiler functions with a half-replaced compiler (GCC's stages, for the same reason). - [x] **`nil` is a symbol, in a static area the collector never moves.** The tagged-word table originally made `nil` an immediate, for the cheapest possible `null` test and a compile-time constant in Rust. Common Lisp says `nil` *is* a symbol — `(symbolp nil)` is true, it has a name, a value cell holding itself, a property list and a home package — and an immediate has nowhere to keep any of that, so every symbol operation needed a special case. Settled SBCL's way: `nil` and `t` are real symbols at fixed, known heap positions in a **static area**, a region at the bottom of the heap that the collector scans but never relocates. `Value::NIL` is therefore an object reference whose index is a compile-time constant, so `null` is still one word comparison, and the special cases disappeared. Four things broke when it landed, none of them in new code; see `book/src/part-2-reading-and-running/11-the-trouble-with-nil.md`.

- [x] **Keywords now, packages in phase 2 — and keywords are the smallest package system.** Common Lisp says a keyword is a symbol in the `KEYWORD` package, which means `foo` and `:foo` have the **same name** and are **different symbols**: `(symbol-name :foo)` is `"FOO"`, and `(eq :foo 'foo)` is false. A symbol table keyed on the name alone cannot express that, so keywords cannot be bolted on without deciding something about namespaces.

  The cheap alternative — interning `:foo` under the name `":FOO"` — was rejected. It makes `symbol-name` quietly wrong, and wrong in a way nothing detects until `symbol-name` is exposed to Lisp. `symbol-name` is therefore a primitive now, and `tests/lisp/keywords.lisp` checks it against SBCL, so the claim is testable rather than asserted.

  What exists is a `HOME` slot on every symbol and a symbol table keyed on *(namespace, name)*, with exactly two namespaces (`home::CURRENT` and `home::KEYWORD`) and none of the machinery: no `use-package`, no `export`, no `::`, no `*package*`. A keyword's value cell holds the keyword itself — CLHS says a keyword is a constant variable bound to itself — so `:foo` evaluates without the evaluator knowing keywords exist. Any other colon (`:`, `::foo`, `foo:bar`) is a read error rather than an ordinary symbol with a colon in its name, because the second would read without complaint today and mean something different later.

  **Packages proper stay tier 1, phase 2.** Nothing is blocked by their absence: `%`-prefixed internals are what every implementation does, and the full system — `use-package`, `shadow`, `export`, `::` versus `:`, package locks, `*package*` at read time — is several hundred lines against the rule 7 budget, for problems that are currently cosmetic. It also wants a hash table per package, which is group C and not built, so building it now would mean building it on lists and rebuilding it later.

  One scheduling note: packages belong at the **start** of phase 2, not inside it. The compiler's sources are written during phase 1, and packages landing after self-hosting begins means re-packaging every file mid-bootstrap. When they arrive, `symbol::HOME` stops being a small integer and becomes a pointer to a package object; nothing else in the symbol representation has to change.

  **Decided in #41** (phase 2): packages are **Lisp objects in the tier-1 library**, not Rust structures. The Rust reader and Rust's `intern` keep their single flat list as the *system symbol table*, so the bootstrap — and the interpreter, which is tier 0 — never learns about packages. When the library loads it creates `COMMON-LISP` (`CL`), `KEYWORD`, `QUOKKA` and `COMMON-LISP-USER` (`CL-USER`) and **adopts** every existing symbol: a name among the standard's 978 `COMMON-LISP` symbols (a data file generated once from SBCL) into `COMMON-LISP`, a keyword into `KEYWORD`, everything else into `QUOKKA`. From then on `symbol::HOME` holds the package — **except for keywords**, which keep the small integer `1`, because Rust must recognise a keyword (for `keywordp`, the printer's colon, a value bound to itself) without knowing what a Lisp package object is (#43) — and new symbols are made by the Lisp `intern`. **One internal package**, `QUOKKA`, for every implementation name; user-facing extensions get packages of their own in their phases. **The `%` prefix stays** — it still says *implementation, not API*, as inside SBCL's packages, and nothing is renamed before the fixpoint. **The useful core** of the package system is tier 1 (`defpackage`, `in-package`, `*package*`, `intern`, `find-symbol`, `export`, `use-package`, nicknames, `pkg:sym` and `pkg::sym`); `shadow`, `import`, `unexport`, `rename-package`, `delete-package`, `do-symbols` and package locks arrive when something needs them. Because reading and printing a prefix needs `*package*` and use lists, the Lisp reader and printer follow packages directly in phase 2's order. Differential files run in `COMMON-LISP-USER`, as SBCL's oracle does.


- [x] **Hash tables hash contents, not addresses.** An `eq` or `eql` hash table in a real Lisp hashes an object's identity, and Cheney's collector moves objects — so an address-based hash is correct until the next collection and silently wrong afterwards. Four ways out were considered: content hashing only; a stable hash word stored in every hashable object; rehashing live tables after each collection (what SBCL does); and pinning hashed objects in the static area.

  Settled on **content hashing**, because what is actually blocked by the absence of hash tables is content-keyed: the obarray (strings), and the compiler's symbol and label tables. The collector gains nothing to do, which keeps #3 as it is through phase 1's image work.

  *Revised by #64 (step Q):* `*print-circle*` needed identity keys, and `eq`/`eql` tables now take any object, hashing one without contents by address and rehashing after the collector marks the table stale — the third option above. What follows describes the table before that.

  What this costs, stated plainly: keys may be fixnums, characters and symbols in an `eql` table, and additionally strings in an `equal` one. Any other key — a cons, a vector — is **refused with an error** rather than quietly hashed by something unreliable. `(make-hash-table :test #'eq)` therefore exists but cannot take the keys a real Common Lisp would allow, which is a divergence from SBCL under rule 6 and is why it signals loudly instead of guessing. Identity hashing comes back on the table when there is a concrete use for it, most likely alongside phase 1's image work, which touches the same code. See [#22](https://github.com/quokka-lisp/quokka-lisp/issues/22).

- [x] **`setf` was pulled forward from tier 1 into tier 0.** The tier table puts `setf` expanders in tier 1, and that is still right for the *extensible* mechanism — `define-setf-expander`, `defsetf`, and the machinery `defstruct` needs to make its accessors settable. What moved is a fixed-place `setf`: variables, `aref`, `svref`, `gethash`, `symbol-function`, `car` and `cdr`.

  The reason is testing, not convenience. Writing a vector element or a hash-table entry has no name in Common Lisp other than `(setf (aref v i) x)` and `(setf (gethash k h) v)`. Without `setf`, the only way to write either was `%set-aref` and `%set-gethash` — Quokka-only names SBCL has no counterpart for, so those behaviours were not *different* from the oracle's but **inexpressible to it**. Two of the three things tier 0's group C added were therefore unverifiable against the standard, which is a hole in the main defence against implementing Lisp wrong. Twenty lines of prelude closed it, and the mutation tests moved from Rust assertions back into `tests/lisp/`.

  What is still tier 1 is the extensibility. A program cannot teach this `setf` a new place; it knows a fixed list. `defstruct` will need the real expander.

- [x] **The extensible `setf` is built on tier 0's, not beside it** (#52, step H). - [x] **The last three special operators are tier 1** (#53, step I). CLHS 3.1.2.1.2.2 lets a special operator be a macro, and none of the three is in the interpreter's table, so the interpreter never learns them. **`progv`** is a library macro over a recursive `%progv` that binds one name per level through the compiler form `%dynamic-bind`, which emits one new instruction, `DBIND-SYMBOL` — `DBIND` with the symbol from the stack — plus a `makunbound` primitive for names given no value: every binding is an ordinary record, restored by everything that restores a `let`. - [x] **Bignums: the algorithms in Lisp, the boundary in Rust** (#16, step L). Rust owns the representation and what is bounded by it: a `Bignum` object of raw slots, a sign word and **limbs of 30 bits, sign and magnitude** (as CPython's `int`) — thirty so that a limb product plus a carry is still a fixnum and the limb loops in Lisp never need bignums themselves; normalising (a value that fits is always a fixnum, so a bignum never equals a fixnum), comparing and hashing, justified under rule 9 as one pass over an object whose allocation already touched every limb. Lisp owns addition, multiplication, division (Knuth's algorithm D), printing and the bit operations (on two's complement by conversion, as CPython). **The boundary is a fallback in the machine**: when `+ - * = < > %quotient rem` fail with overflow or meet a bignum, `Vm::call_value` calls `%generic-+` and its kin with the same arguments, so the fixnum path is untouched. - [x] **Conditions are flat, not a class hierarchy.** Tier 0 asks for `error` and `handler-case`, and Common Lisp's are built on CLOS: `simple-error` is an `error` is a `serious-condition` is a `condition`, programs add their own with `define-condition`, and `handler-case` matches by *subtype*. Quokka has no class system until phase 3.

  So a condition is an object with a type symbol, a message and some data, and matching is flat: a clause naming `error`, `condition` or `t` catches everything, anything else must name the condition's own type exactly. The evaluator's own errors are given the standard's type names — `type-error`, `unbound-variable`, `undefined-function`, `program-error`, `control-error`, `arithmetic-error` — so code written against Common Lisp catches what it expects, and the differential tests check that it does.

  What this costs: a program cannot define a condition type. `(error 'my-error)` works here and is not portable, because a real Common Lisp requires that symbol to name a class. That half is therefore untestable against the oracle, and is covered by Rust tests. `define-condition` and subtype matching arrive with the class system in phase 3, along with `handler-bind` and restarts.

  `HeapExhausted` and `BudgetExhausted` are deliberately **not** conditions: neither is a fault in the program being run, and a handler catching them would be catching the machinery. Heap exhaustion becomes a `storage-condition` in phase 3, when there is a hierarchy to put it in.

(4) **One float format**: the four float names are one type, as CLHS 12.1.4.1.1 allows; `-0.0` is a kind of its own so that a range holding 0.0 holds it and `(member 0.0)` does not. (5) **No base strings**: `base-char` upgrades to `character`, so `base-string` is `string`, and an array made with `:element-type 'base-char` is of type `(array base-char)`; SBCL differs only because it has base strings. `upgraded-array-element-type` and `make-array`'s element kinds go through `subtypep` (the common names answered at once). (6) **`deftype`** stores an expander of `(form env)` on the name's plist, made by `defmacro` under a hidden name with unsupplied optionals defaulting to `*` and the body in a block named after the type; a chain of expansions longer than a hundred is an error (SBCL loops). `ctypecase` and `check-type` signal `type-error` until restarts exist. No Rust.

- [x] **Classes and instances** (#124, CLOS sub-step 2, six decisions). (1) **Two heap types of their own**, `StandardInstance` (wrapper, slot vector) and `FuncallableInstance` (function, wrapper, slot vector), in `crates/quokka-vm/src/instance.rs`, with eight constant-time primitives; not the `Instance` a structure is (as `docs/clos.md` first said), because every structure path reads an `Instance`'s slot 0 as a layout. The slots are in a vector of their own, PCL's representation, so that redefinition and `change-class` can replace them while the instance stays `eq`. (2) **The machine calls a funcallable instance's function** with the same arguments, once: the setter refuses another funcallable instance as the function, so no loop is needed; with no function, calling one is `NotAFunction`. `functionp` is true of one, `compiled-function-p` false, as SBCL answers for a generic function. (3) **Classes are standard instances with a fixed slot layout** (the twelve slots of class `class`, inherited unchanged by every metaclass), read by hand-written `%class-…` functions; slot definitions likewise. (4) **The bootstrap is Closette's, in four idempotent stages** in `lisp/library/clos.lisp`: class objects, metaclass wrappers, direct slots, finalization; a warm rebuild finds the classes and refills them, and a class whose instance slots did not change keeps its wrapper, so instances survive (`a_rebuild_keeps_classes_and_their_instances`). (5) **Every object has a class**: the classes of CLHS figure 4-8 plus SBCL's `fixnum`, `bignum`, `double-float` and simple array classes; condition classes (metaclass `condition-class`) from the prelude's lattice; a structure's class made the first time it is asked for, so `structures.lisp` is untouched. Class names and class objects are types: `typep` asks the class precedence list (CLHS 4.3.5's algorithm), `subtypep` has a kind `:instance` whose terms name class objects. (6) **`make-instance`, `initialize-instance`, `shared-initialize`, the slot functions and accessors are ordinary functions** until generic functions exist (sub-step 3), Closette's order; MOP-only names are QUOKKA symbols until sub-step 7. Rust 242.

- [x] **Generic functions** (#124, CLOS sub-step 3, six decisions). (1) **A generic function is a funcallable instance of `standard-generic-function` whose function is a discriminating closure**, `(lambda (&rest args) (%dispatch gf args))`, in `lisp/library/generic-functions.lisp`. (2) **The cache** maps the list of the required arguments' classes (an argument `eql` to some method's `eql` specializer keyed by that specializer) to an effective method; it is emptied when the generic function's epoch is not the current `%dispatch-epoch`, a fresh cons made whenever a class is defined or a method added or removed. A cons and not a counter: a counter keeps counting across warm rebuilds, so C2 and C3 held different numbers. (3) **Effective methods are closures**: a method function is `(lambda (args next) ...)`, NEXT the effective method of the methods after it; standard combination builds the around chain, the before/primary/after core, and, when the generic function takes keywords, the CLHS 7.6.5 check that every keyword is accepted by some applicable method (each method itself allows other keys). (4) **Metaobjects keep slots at fixed places** (`%gf-…`, `%method-…`), checked when the file loads, so dispatch never dispatches; `slot-value` stays an ordinary function. (5) **The instance protocol and accessors are generic**: `make-instance`, `allocate-instance`, `initialize-instance`, `reinitialize-instance`, `shared-initialize`, `slot-missing`, `slot-unbound`, with standard methods calling `clos.lisp`'s `%` workers; readers and writers are `standard-reader-method`s and `standard-writer-method`s. `clos.lisp` defines none of the public names, or a warm rebuild would replace each generic function with a plain one. Initarg checking adds the keywords of applicable `allocate-instance`, `initialize-instance` and `shared-initialize` methods (CLHS 7.1.2). (6) **Only standard method combination**; `defgeneric` refuses any other until sub-step 6. The fixpoint test describes an instance by its class's name: walking a generic function's slots by depth alone took 20 GB. No Rust.

- [x] **Printing through `print-object`** (#124, CLOS sub-step 4, six decisions). (1) **The printer sends only instances, structures and conditions to `print-object`**; a cons, a symbol, a number, a string, an array, a function and a hash table go straight to the printer's own code, as before, unless `%print-object-on-built-in` is true, which `add-method` sets for a `print-object` method on a built-in class (or an `eql` specializer on such an object) and never clears. CLHS 11.1.2.1.2 leaves such a method undefined and SBCL honours one on `cons` but not one on `integer` at top level; Quokka honours it everywhere. Rejected: calling `print-object` for every object, as the letter of CLHS 22.1.3 reads, which puts a generic function call on every element of every list printed; the step budgets of ansi-test and the warm rebuild would notice. A structure whose type has no method but the library's two defaults skips the generic function too: `%printed-plainly-p` keeps that answer for each layout with the dispatch epoch it was found in, because dispatch made printing a list of structures a third slower, measured. (2) **The method on `t` is the printer's own code** (`%print-built-in`, told not to send objects back to `print-object`), so `call-next-method` from any method prints what the printer printed before. (3) **A method's own printing continues its printout**, as SBCL's does (measured): `prin1`, `princ`, `write` and `format` inside a method print at the depth the object was printed at, for `*print-level*`, and share its `*print-circle*` labels, through `%print-nesting`, the depth while the printer runs a method. The object itself is no level; neither is `print-unreadable-object` when not pretty-printing (SBCL's pretty printer counts one). (4) **`*print-circle*`'s first pass runs the methods** into a stream nobody reads, with every object they print noted instead of written (`%noting`), because only the method knows what it prints: `#1=#<BOX #1#>`. A structure with a method of a program's is noted through it; a plain one is walked by its slots, which is cheaper; and the list printer notes each tail as it walks into it, so a circular list ends even when lists go through `print-object`. (5) **A `defstruct`'s `:print-function` or `:print-object` is a `print-object` method on its class**, as in SBCL, added by `%note-structure-defined`, so the most specific printer wins by the ordinary rules; a later `defstruct` without the option leaves the method in place, as SBCL's does; a printer named by a symbol is called by that name when printing, so it may be defined after the `defstruct`. (6) **`print-unreadable-object` follows SBCL's spacing, with an empty identity**: the type (`type-of`, written as `prin1` or `princ` would write it, as the printout is escaping or not) is followed by a space even with no body (`#<POINT >`), and the identity, which in SBCL is the address, is only its leading space, because Quokka's objects move. The default method on `standard-object` writes `#<POINT>`, with no space. `describe` calls the generic function `describe-object` and writes nothing of its own, returning no values; its text follows SBCL's in outline and is tested only in Quokka (CLHS leaves it to the implementation). `with-slots` and `with-accessors` are macros over `symbol-macrolet`. No Rust.
- [x] **Redefinition and `change-class`** (#124, CLOS sub-step 5, five decisions). (1) **Obsolete instances are updated lazily, when a slot is touched**: a class whose local slots change gets a new wrapper and the old one is marked `(:obsolete . shared-cells)`; `%ensure-current-instance`, on every slot access, compares an instance's wrapper with its class's and calls the generic function `update-instance-for-redefined-class` with the added and discarded slots and the property list. CLHS 4.3.6 leaves the time to the implementation; SBCL also updates on every generic function call, and Quokka does not, so that dispatch costs nothing more; differential files never observe the difference. (2) **The obsolete wrapper records the old class's shared slots**, because a slot shared before and local after keeps the shared value (CLHS 4.3.6.1). (3) **What SBCL does, measured**: a redefinition with the same local slots makes nothing obsolete (which the warm rebuild relies on); the *added* slots are every local slot still unbound after the copy, one kept but unbound included (CLHS 4.3.6.1 would keep it unbound), and the discarded slots only those that had a value, all three lists in reverse slot order; an update or a `change-class` whose generic function does not return normally is undone, so the next touch retries; a shared slot's initform is evaluated when its class is defined (`%initialize-shared-slots` in `%finalize-class`), not at the first `make-instance`. (4) **`change-class` keeps the instance and replaces its wrapper and slot vector**, handing `update-instance-for-different-class` a copy of the instance as it was (a standard instance of the old wrapper); the initargs are checked in that generic function's standard method, after the change, as SBCL does. A standard instance and a funcallable one never become each other: they are different heap types. (5) `make-instances-obsolete` gives a class a new wrapper with the same slots. No Rust.
- [x] **Method combination** (#124, CLOS sub-step 6, five decisions). (1) **A generic function holds a method combination object** (`standard-method-combination`: a name and the options its `defgeneric` gave), and **`%combinations` maps each name to a definition**, a function of the options returning a *combiner*, a function of the generic function and its sorted applicable methods returning the effective method. The name is looked up again on every cache miss, so a combination defined again changes every generic function using it, and a warm rebuild keeps a program's combinations (the table is a `defvar`). (2) **Standard and the nine operator combinations build closures**, as before; `and`, `or` and `progn` are closures that stop as those operators do, any function operator is applied to the methods' values, and one primary method with `:identity-with-one-argument` (every built-in but `list`; false by default in a short form) is called alone so its values pass through. (3) **A long form compiles**: its body returns an effective method form with `call-method` and `make-method`, compiled once per cache miss into `(lambda (%emf-args) ...)` with both as local macros (`%form-effective-method`), as `docs/clos.md` decided; a make-method is a function of the argument list like a method's, so `call-next-method` with new arguments reaches its form with them; `:arguments` variables (with defaults, supplied-p variables and `&aux`) are bound in the body to their own names, as in SBCL, and the effective method binds those names in order, each by the argument's place among the generic function's own parameters. A short form whose operator is a macro or special operator is compiled the same way, without `call-method`. (4) **What SBCL does, measured**: an operator combination's options are checked at `defgeneric`, a long form's only when the generic function is called; no primary method is checked before methods with qualifiers the combination does not accept, under standard combination too, and its error (like `no-applicable-method`'s, changed to match) is neither a `program-error` nor a `simple-error`; `invalid-method-error` and `method-combination-error` signal `program-error`; a long form's `:required` group left empty and two methods with the same specializers in one group (except when the only group takes every method) are `simple-error`s; a `defgeneric` without `:method-combination` keeps the combination the function had. (5) An error in a long form's body, or a form that does not compile, reaches the caller and leaves nothing in the cache. No Rust.
- [x] **MOP introspection and the `objects` group** (#124, CLOS sub-step 7, six decisions). (1) **`QUOKKA-MOP` is a package of its own**, made in `packages.lisp` before `QUOKKA`, which uses it; its names (`%quokka-mop-symbol-names`: the metaobject classes and the readers) are adopted into it as external symbols, as the standard's names are into `COMMON-LISP`, so the library reads them without a prefix and a program sees them as `QUOKKA-MOP:CLASS-SLOTS`, as SBCL's are `SB-MOP:CLASS-SLOTS`. (2) **The readers (`lisp/library/mop.lisp`) are ordinary functions**, each checking first the kind of metaobject it is given (`%check-metaobject`, an `error` like SBCL's `no-applicable-method`), where AMOP makes them generic; a structure class's slot definitions are made from its layout when first asked for and kept until the layout's slots change: this is the introspective half only (`docs/clos.md`), and a method on a reader could change only what the system says about itself; `method-function` returns Quokka's own method function, of the argument list and the next effective method, not AMOP's of the argument list and the next methods. (3) **A specializer keeps its own direct methods** (a class on its property list, an `eql` specializer in a second slot), kept by `add-method` and `remove-method`; a first version kept them in an `eq` hash table, which hashes by address and, rehashed after a collection, conses in an order that differs between generations, so C2 and C3 differed and `a_rebuilt_world_is_the_same_world` failed. (4) **What the `objects` group found**: a generic function given more arguments than its lambda list takes signals `program-error` (first built as a closure around each cached effective method, which cost a fixed-arity call about 4% more steps; now the arity is kept in a slot of the generic function when its lambda list is set, and `%dispatch` checks both ends in the walk over the arguments it already made, which also stopped it walking the lambda list on every call, so a call costs about a fifth fewer steps than before the check; SBCL checks only once its discriminating function has cached, and reports `no-applicable-method` on a first call); `class-name` and `(setf class-name)` are generic functions, and a `defclass` of a name that is no longer its class's *proper name* (CLHS 4.3.1) makes a new class; `defgeneric` and `defclass` options given twice, and a default initarg given twice, are `program-error`s (SBCL accepts a repeated `:argument-precedence-order` and `declare`); `slot-value` gives the first value of `slot-unbound` and `slot-missing`, `slot-boundp` the truth of `slot-missing`'s; `make-load-form` is a generic function with CLHS's default methods and `make-load-form-saving-slots` writes SBCL's two forms; `allocate-instance` makes a structure with every slot nil; a slot's readers and writers are listed newest first, as SBCL lists them. (5) Four tests SBCL also fails are counted as such (`tests/ansi/deferred.lisp`): an undefined function is not a `program-error`, `call-next-method` with arguments that change the applicable methods is not checked, and `shared-initialize` does not check its initargs. (6) `make-load-form` and `make-load-form-saving-slots` left the deferred list; nothing calls them until there is a `compile-file`. (7) The review's minors, fixed after: **a structure's class and its layout find each other directly**, the class kept under the structure name's `%structure-class` property and the layout on the class's property list, so that `class-of` and `allocate-instance` keep working after `(setf class-name)`, and a `defclass` of the old name makes a new class without taking the structures' (SBCL does the same, with a warning); the name of a built-in class cannot be changed (SBCL refuses with a `simple-error`, and a renamed `integer` would let `defclass integer` replace it in `find-class`); `class-prototype` of a built-in class is an object of the class, as in SBCL (none for `t`, as in SBCL, nor for classes whose objects Quokka cannot make yet); `make-instance` of a structure class fills the slots' initforms, evaluated by `eval` in the null lexical environment, and calls `initialize-instance`, as SBCL does, with `initialize-instance` and `shared-initialize` methods on `structure-object`. No Rust.
- [x] **Conditions are objects** (#125, phase 3 step B, sub-step 1; the design is `docs/conditions.md`). (1) **A condition is an instance of its condition class**, a `StandardInstance` whose class has metaclass `condition-class`; `condition` is not a subclass of `standard-object`, as in SBCL. `ensure-class` makes condition classes too: one redefines only a condition class (`%metaclass-kind`), its default superclass is `condition`, its superclasses must be condition classes and already defined (SBCL refuses an undefined parent with a `type-error`; a placeholder could later become a standard class, which the review found), a placeholder that standard classes wait for is not adopted (the condition is a new class, as in SBCL), and only `condition` itself has `t` as its superclass. (2) **`define-condition`** is a macro over `ensure-class` with `defclass`'s slot syntax and the options `:default-initargs`, `:documentation` and `:report`; **`make-condition`** fills slots from initargs, default initargs and initforms and, as in SBCL, ignores an initarg no slot takes; `make-instance` of a condition class makes one too, as in SBCL. (3) **The standard types get CLHS's slots** (`lisp/library/conditions.lisp`), named in `QUOKKA` as SBCL's are in `SB-KERNEL`, with CLHS's readers. (4) **The library's own form `(error 'type "message" data...)` stays**: class `condition` has two slots, `%message` and `%data`, for such a condition, which reports its message (filled from sub-step 2, when `error` is Lisp); about 240 library calls and every compiler error use the form, and SBCL refuses it. (5) **A report** is kept on the class's property list and found along the precedence list; `print-object` on `condition` prints `#<TYPE>` when escaped and the report when not; the standard types report in SBCL's words, on one line (SBCL breaks them with the pretty printer). (6) **Condition types are classes in the type algebra**: the `:condition` kind is gone, condition types are `:instance` terms, and the machine's own condition objects, until the library stops making them (sub-step 3), are of their class by `class-of`. (7) Reports are SBCL's text as SBCL prints with `*print-pretty*` false, names with their package (`%name-with-prefix`); a second `:report` wins and an odd initarg list is refused, as in SBCL. Left as minor: duplicate slot names and `define-condition` over a standard class's name are refused (SBCL accepts both), and a `simple-condition` without a control reports the default text (SBCL errs). (8) ansi-test 10,802; four tests fail until sub-steps 2–3 make the machine's errors instances, because they read a CLHS slot from one of the machine's old conditions. No Rust.

- [x] **One lexical environment in the compiler** (#111 item 2, 25 Nov 2026). The compiler described where a form stands with three structures: `env`, the scopes, passed as an argument; `%open`, a global list of what is open between the form and the start of its function (unwind records, tagbodies, a function's edge), which `go` reads to choose between `JMP-TAG` and `GO`; and `%local-macros`, a global list of `macrolet` expanders, which could not know that an `flet` further in had taken a macro's name and so was given an entry with no expander to say so. They are one list now, innermost first, each entry `(kind . contents)`, nil the null lexical environment, and the same object is a macro's `&environment`. Four kinds are **run-time scopes** the machine builds a link for (`:variable`, `:function`, `:block`, `:tag`) and `%lookup` counts them, so `(depth, index)` is what it was; seven exist **only while compiling** and are stepped over (`:macro`, `:symbol-macro`, `:special`, `:notinline`, and the open entries `:record`, `:tagbody`, `:lambda`). A local function hides a `macrolet` macro, and the reverse, by which is met first. Compiling is re-entrant in all of it without saving anything, and the compiler's globals are down to the code and the constants. Emitted code is the same instruction for instruction. Rejected: SBCL's shape, a `lexenv` structure with a list per namespace — the machine's scope chain is one chain across namespaces, so the interleaving that `depth` counts would have to be recorded a second time; and a record of three fields, which is the three structures under one name. One behaviour changed on purpose: **a `macrolet` expander is compiled in the compile-time part of its environment** — outer `macrolet` and `symbol-macrolet` definitions and declarations — as CLHS `macrolet` says and SBCL does; before, it saw outer local macros but not symbol macros. A library function reads an environment only through `%environment-macro`, `%environment-symbol-macro` and `%environment-function-p`. With it: the constants of a function being compiled have an `eq` table beside their list (#111 item 5; a `progn` of 500 calls to different functions ran out of the REPL's step budget in the linear search, and compiles in 0.4 s), and a tagbody's labels are handed out in order instead of searched for.
- [ ] **The compiler's state becomes per-process special variables** (#111 item 1, decided 25 Nov 2026; to build in phase 3). The compiler keeps its work in progress in global variables — `%code`, `%constants`, `%constant-count`, `%constant-table`, `%pending-name`, `%toplevel-form` — saved and restored by hand around a nested compilation. That is re-entrant and not safe for two processes compiling at once: a switch between them lands in the middle of both. They become special variables bound in `compile-form`, so each process's compilation has its own. Two things must exist first: per-process dynamic bindings (#34 item 3; today a binding is shallow, in the symbol, and the scheduler would have to swap them at a switch), and special variables in tier 0, because the interpreter runs the compiler in the cold build. Rejected: one compile lock (simple, and it makes a debugger that evaluates a form while another process is stopped inside a compilation wait for it — the first two-process case there will be). The four persistent tables (`%special-variables`, `%constant-variables`, `%compiler-macros`, `%global-symbol-macros`) are shared on purpose, and writes to them need the same answer as every other shared table in phase 3.
- [ ] **A debug setting keeps a function's original arguments in its frame** (#111 item 4, decided 25 Nov 2026; to build in phase 3). A frame holds the saved pc, the frame pointer, and the *caller's* function and environment; `CALL` pops the arguments into the callee's scope, where `setq` may change them. Phase 3's gate is to fix a function from inside an error and retry the frame, and retrying needs the callee and the arguments it was called with. So under a debug setting — SBCL's `(debug 2)` and above does the same — compiled code keeps its original arguments (and the callee) where the debugger can find them, at the cost of the frame's size and of objects living as long as the call; without it, the debugger says a frame cannot be restarted. Rejected: always keeping them (every call pays), and re-reading them from the scope (wrong after a `setq` of a parameter).
- [ ] **Source of truth, again** (raised 27 Nov 2026). The decision above says files are the truth and a world caches them; the environment design (*The world is a database of definitions*) says a running world is the truth and files are a view written from it. A reconciliation we proposed: committing writes each changed package back to its file, so between commits the world is ahead of the files, and at every commit the two agree again. Images would still not be committed. To decide before phase 6, and before then if the who-calls index or keeping source in definitions is built.
